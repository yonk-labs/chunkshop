# chunkshop 0.8.0: teaching the code graph to stop lying

So you want your coding agent to answer "what calls this function?" across a
whole repo. Sounds easy. It is not easy. The hard part was never the vector
search — it's getting an honest map of the code in the first place. And for the
last few releases, chunkshop's map only covered five languages and quietly told
a few small lies. 0.8.0 fixes both.

Here's the deal: chunkshop turns a codebase into chunks *and* a graph of
`CALLS` / `INHERITS` / `IMPLEMENTS` edges in Postgres, so an agent can do
retrieval and traversal off the same table. This release does three things to
that graph — it goes **wider**, gets **more precise**, and stops **making
things up**.

## Wider: 5 → 10 languages

The `codeparse` layer now ships real tree-sitter grammars for **ten**
languages, not five: Python, Java, Go, TypeScript, JavaScript — and now
**Rust, C, C++, C#, and Ruby**. Real grammars, not regex that squints at your
code and hopes. (The regex fallback still exists, but only as a safety net when
you skip the `[code]` extra.)

Each new extractor does the language-specific thing you'd want: Rust groups
methods under their `impl`/`trait`, C++ handles inline *and* out-of-line
`Class::method` definitions, C# knows its calls are `invocation_expression`
(because of course they are), Ruby does best-effort `call`-node detection
because Ruby is Ruby. Install `chunkshop[code]`, point it at a repo, get
symbol-aware chunks and cross-file edges. Done.

## More precise: import-aware resolution

Here's a problem that's been lurking. Two files define a function called
`helper`. A third file calls `helper()`. Which one did it call? The old
resolver shrugged and emitted an edge to *both* — a guess, tagged
`ambiguous_name`, at low confidence. Multiply that across a real codebase and
your graph gets noisy fast.

But the caller file already told us the answer. It has an `import`. We were
parsing those imports and then... throwing them away. (Yeah. I know.)

0.8.0 keeps them. When a name is ambiguous, the resolver checks what the caller
actually imported and, if exactly one candidate's module matches, collapses the
guess into a single precise edge tagged `import_resolved` at full confidence.
It works across languages — Python's `from a import helper`, Rust's `use
crate::a::helper`, C's `#include "a.h"` — because it matches the candidate
file's stem against the caller's import tokens. And it's conservative: if the
imports don't decide it, you keep the old fan-out. We never drop an edge, we
just stop guessing when we don't have to.

This is the "right-sized" version of cross-file resolution, by the way. A full
stack-graphs / SCIP resolver is the heavyweight answer (and it's coming, on the
Rust side). Import-aware name matching is the 80% answer that ships today and
runs in milliseconds.

## Stopped lying: the orphan-edge bug, and proving it's dead

Now the uncomfortable part. While hardening the graph, we found a real bug in
our *own* extractor. When a call happened inside a nested function, we
attributed it to that nested function — which we never actually emitted as a
node. So the edge pointed at a source node that didn't exist. An orphan. In a
graph. The one data structure where dangling pointers are the whole problem.

We fixed it (calls now roll up to the outermost emitted symbol), and Python
symbol spans now include their decorators while we were in there. But fixing a
bug isn't the interesting part. *Proving it's gone* is.

So we ran the extractors against real code and counted:

- **chunkshop's own Rust tree** — ~1,300 symbols, ~9,400 calls: zero orphans.
- **Postgres 16.3**, the whole `src/` tree — 1,269 C files, 25,431 symbols, and
  **250,000 call sites**: zero orphans, zero out-of-bounds spans, zero crashes,
  zero regex fallback. In about 21 seconds.

A quarter-million call sites of genuinely gnarly C — macros, generated parsers,
K&R-isms — and the graph came out clean. That's the test I actually trust.
There's a corpus invariant test in CI now so it stays that way.

## What this means for your Tuesday

If you're building a coding agent or a code-search tool: you can now ingest a
polyglot repo, get a symbol-level graph that spans ten languages, and trust
that an edge points at a node that exists. The provenance is honest, too —
every cross-file name-match is tagged `heuristic`, every AST-direct edge is
`ast`, so a downstream consumer can rank or filter on how sure we are.

Grab it:

```bash
pip install "chunkshop[code]"
chunkshop init --out repo.yaml   # scaffold a cell
chunkshop ingest -c repo.yaml    # chunks + code_edges
chunkshop impact-of --fqn mymodule.my_func --direction callers
```

Full notes are in the [CHANGELOG](../../CHANGELOG.md). The whole thing is open
source — if you point it at a codebase and the graph lies to you, that's a bug,
and I want to hear about it. Go break it.
